# Постоянное подключение Google

С версии 1.5.0 страница подключения использует GIS `initCodeClient` в popup-режиме. Одноразовый код передаётся через nonce и GM storage в OWA, оттуда через `GM_xmlhttpRequest` — в `/owa-calendar-auth/exchange`. Служба обменивает его с Google, проверяет разрешения и аккаунт, сохраняет refresh token и возвращает случайный ключ подключения устройства и краткоживущий access token. Код и токены не включаются в URL.

Перед синхронизацией userscript проверяет срок доступа. Если он истёк, служба получает новый access token через refresh token; повторного входа и выбора аккаунта нет. При HTTP 401 от Google API обновление и повтор запроса выполняются один раз. Сетевые ошибки и HTTP 5xx не удаляют подключение. При настоящем `invalid_grant` Google потребуется повторный вход.

Встречи не проходят через службу. Она хранит только данные доступа Google, адрес и идентификатор аккаунта. Ключ подключения устройства хранится в GM storage, а на сервере его SHA-256 используется как имя зашифрованного файла. Данные зашифрованы AES-256-GCM, каталог имеет права 0700, файлы — 0600. Ключ шифрования и client secret находятся в закрытом файле окружения. Удаление подключения сериализовано с обновлением токена, поэтому завершившееся обновление не восстанавливает удалённую сессию.

## Развёртывание владельцем

1. Используйте существующий OAuth Web Client ID и его client secret. Секрет не должен попадать в git, userscript, страницу подключения или переписку.
2. Оставьте Authorized JavaScript origin `https://mainiken.github.io`. Для обмена popup-кода служба использует этот же origin как `redirect_uri`, согласно [документации Google](https://developers.google.com/identity/oauth2/web/guides/use-code-model).
3. Создайте закрытый `private/auth.env` с `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` и `AUTH_ENCRYPTION_KEY`. Последний — 32 случайных байта в base64, например `node -e "process.stdout.write(require('crypto').randomBytes(32).toString('base64'))"`. Этот ключ нужно сохранять при перезапусках и включать в защищённую резервную копию отдельно от данных.
4. `compose.auth.yml` использует существующую внешнюю сеть Docker `web` и Traefik с entrypoint `websecure` и resolver `letsencrypt`. Задайте `AUTH_HOST` и запустите `docker compose -f compose.auth.yml up -d --build`. Порт службы не публикуется напрямую. Userscript использует HTTPS `/owa-calendar-auth` на домене, заданном в `AUTH_SERVICE` и метаданных `@connect`.
5. Проверка: GET `/owa-calendar-auth/health` возвращает `{"ok":true}`. Остальные операции требуют POST JSON и заголовки Origin и X-Requested-With, дальнейшие операции — также ключ устройства в Authorization. Cookies и CORS не используются. Не включайте логирование тел запросов и заголовка Authorization на reverse proxy.
6. Опубликуйте обновлённые страницу подключения и userscript вместе. Версия старого userscript блокируется на новой странице входа. Пользователю достаточно обновить скрипт и один раз подключить Google заново. Календарь и метки событий не меняются.

## Настройка Google, необходимая для длительного доступа

В **Google Auth Platform → Audience** приложение с внешней аудиторией должно быть **In production**. В режиме **Testing** Google ограничивает жизнь refresh token семью днями для запрашиваемого Calendar scope. Переключение статуса и возможная проверка приложения выполняются владельцем в Google Cloud Console. Сервер не может отменить это ограничение. [Срок жизни refresh token](https://developers.google.com/identity/protocols/oauth2#expiration).

При отзыве разрешения пользователем или Google, изменении политики организации или удалении серверных данных повторный вход необходим. При обычном часовом истечении access token он не нужен.

Проверки: `npm test` включает имитацию Google, перезапуск службы, несколько циклов продления, отзыв, сетевой сбой, гонку отключения, HTTP-проверки и обновление токена из userscript. Реальный Google OAuth требует отдельного прохода пользователем в его браузере; health-check не подтверждает настройки Audience или успешность OAuth.
